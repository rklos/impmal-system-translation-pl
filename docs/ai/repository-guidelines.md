# Repository Guidelines

Use these instructions for every task in this repository. They summarize verified project
facts and define the checks required before handing work back for review.

## Project Scope

This project builds a Polish core-translation module for the Imperium Maledictum Foundry
VTT system. It combines language JSON files, custom TypeScript and SCSS, and unified diff
patches for upstream scripts and Handlebars templates.

Current compatibility belongs in `src/module.json`, not in this document. Package-specific
upstream repositories and versions belong in their `src/packages/<package>/index.ts` files.

## Repository Map

| Path | Responsibility |
|------|----------------|
| `src/module.json` | Foundry VTT module metadata and compatibility |
| `src/packages/impmal/` | ImpMal language, scripts, styles, and patches |
| `src/packages/warhammer-library/` | WHLib language and package metadata |
| `src/packages/custom/` | Polish-specific overrides and custom behavior |
| `src/utils/` | Shared runtime utilities |
| `tools/commands/` | Reporting, synchronization, and patch CLI commands |
| `tools.config.ts` | Tool configuration for patchable packages |
| `.vite/` | Build-time patch loading |
| `docs/` | Human documentation |
| `docs/ai/` | Task-focused AI instructions |

## Working Rules

- Start substantial work from an updated `main` on a dedicated branch.
- Inspect the working tree before editing and preserve unrelated user changes.
- Keep changes limited to the requested outcome.
- Use the current code and configuration to resolve stale documentation.
- Use exact upstream release tags when comparing or patching external projects.
- Keep separate concerns in reviewable steps. Do not hide translation changes inside a
  patch refresh or a dependency update.

## Use Repository History

Check history when a task repeats an established maintenance or release operation.

```bash
git log --oneline -- <relevant-path>
```

```bash
git show <commit>
```

Use history to learn file groupings, review boundaries, and project terminology. Confirm
the pattern against current code before following it. A commit from an unmerged branch or
an older architecture is evidence, not a current instruction.

The established change boundaries are:

- keep an automated WHLib synchronization isolated so its imported changes are clear;
- separate refreshed or removed patches from patches for newly discovered strings;
- prefer an existing upstream localization key over hardcoded Polish text;
- leave an uncertain translation unchanged and request review instead of guessing;
- keep a module release version bump separate from compatibility and translation work;
- update tool documentation with changes to tool commands or behavior.

## Generated and Temporary Data

- `dist/` is generated by the build and is ignored by Git.
- `src/packages/<package>/temp/` is working data used by patch commands and is ignored by
  Git.
- `src/packages/<package>/patches/` contains tracked source patches.
- Modify tracked files at their repository paths. Do not prepare shadow replacements in
  `/tmp`.
- A scratch directory is appropriate for a clean, immutable upstream checkout or a
  disposable audit report.

## Commands

| Command | Purpose |
|---------|---------|
| `npm ci` | Install the exact dependency set from `package-lock.json` |
| `npm run build` | Type-check, build, and combine translation JSON files |
| `npx eslint .` | Attempt to lint TypeScript and JavaScript with the repository configuration |
| `npm run report` | Compare supported upstream versions with their latest releases |
| `npm run sync wfrp4e` | Import WHLib translations from the WFRP4e Polish project |
| `npm run sync source` | Merge local translations into current upstream language files |
| `npm run patch download` | Populate patch working trees from upstream default branches |
| `npm run patch apply` | Apply tracked patches to package working trees |
| `npm run patch create` | Rebuild tracked patches from complete working trees |

Networked commands require GitHub access. If CLI access is denied by the sandbox, request
network permission and rerun the CLI command. Do not switch to browser automation only to
avoid the approval request.

## Code Conventions

- Follow `eslint.config.js` and the existing code style.
- Use TypeScript strict mode and avoid weakening types without a Foundry-specific reason.
- Use 2 spaces, single quotes, semicolons, and trailing commas in multiline structures.
- Keep package-specific behavior inside its package.
- Keep reusable development behavior under `tools/`.
- Add comments only for non-obvious intent, constraints, or workarounds.
- Prefer current configuration and task playbooks over copied generic rules.

## Validation

Choose checks based on the changed files:

| Change | Required checks |
|--------|-----------------|
| Documentation only | `git diff --check`, headings, and internal links |
| Language JSON | `npm run build` and review placeholders and HTML |
| TypeScript or JavaScript | `npx eslint .` and `npm run build` |
| SCSS or build configuration | `npm run build` |
| Patch files | Exact-release patch audit, `npm run build`, and runtime smoke test |
| Compatibility metadata | Upstream release verification and `npm run build` |

The current ESLint command exits while loading `import/no-unresolved` with ESLint 10.0.3,
before it checks project files. Run it so a future configuration fix is detected. Until
then, report this as an existing validation blocker rather than claiming that lint passed.

Read command output and inspect `git diff`. A zero exit code is not sufficient when a tool
catches errors and continues.
